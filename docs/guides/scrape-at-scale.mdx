# Scraping at Scale

When one page isn't enough — pages 1..N, whole sites, media-heavy catalogs.

## Batch — pages 1..N / many URLs

`webrain_batch` runs one schema over many URLs using concurrent tabs
(crawl4ai `arun_many` + MemoryAdaptiveDispatcher style):

```json
{
  "op": "extract",
  "urls": ["https://example.com/products?page=1", "...&page=2"],
  "base_selector": ".product",
  "fields": [{ "name": "title", "selector": "h3", "type": "text" }],
  "concurrency": 8
}
```

`op` variants:

- `fetch` — read visible text
- `extract` — run a CSS/XPath schema (zero-LLM)
- `interact` — run an async JS `interaction` in parallel tabs (click
  Load-More / infinite-scroll / form fill), then optionally extract a schema —
  one call replaces N serial agent loops
- `screenshot` — save full-page PNGs to `dir`

Optional `cdp_urls` (list) fans the batch across N CDP backends round-robin —
per-proxy isolation in one call, no subagents. Optional `output` persists the
full payload to disk (survives temp-file GC between turns).

<Note>
  `webrain_batch` requires a browser backend — if no browser is running it
  errors fast (5s timeout).
</Note>

### Read the report, not the request

Every reply carries `stats`, and the numbers there are **measured**:

```json
{"total":8,"ok":8,"errors":0,"requested_concurrency":4,
 "effective_concurrency":4,"single_target":false,
 "ms_total":3853,"ms_wall":1464}
```

- `effective_concurrency` is the number of tabs the batch **really obtained**
  (summed across `cdp_urls`), so `2` next to `requested_concurrency: 4` means two
  workers won and two did not — not a display bug.
- `single_target: true` means the connection holds **one** tab (lightpanda, guest
  Chrome): the queue runs serially and no `concurrency` value changes that. It is
  still a pass when `ok` equals `total`.
- `ms_wall` far below `ms_total` is the parallelism you actually got; the two
  within a few ms of each other means serial.
- A batch that dies as a whole answers **once per URL**, with the same error in
  each row — `total` always equals the number of URLs you sent.

### Wait on the list, not on the first card

`wait_selector_state` is satisfied by **any** match. Before the fix only the
first DOM match counted, and an SPA list page renders the same cards twice —
a hidden mobile container first, the visible desktop copy second — so `visible`
never arrived and each page burned the whole `wait_timeout_secs`. Measured on
`masoutis.gr` (27 search URLs, `wait_selector: "div.product"`, `concurrency: 6`,
2026-11-06):

| setting | wall | rows |
|---|---|---|
| `visible`, 30 s timeout (before the fix) | **159.4 s** | 27/27 ok |
| `attached`, 30 s timeout | 33.6 s | 27/27, same `found` |
| `attached`, **6 s** timeout | **10.1 s** | 27/27, identical data |

`ms_total` was 858 s, of which 27 × 30 s = **810 s (94 %)** was pure wait; real
page work was ~1.8 s/URL. So before blaming `concurrency` or the site, compare
`ms_total` with the page times.

- `wait_selector_state: "attached"` + `wait_timeout_secs: 6` on a list.
- Anchor on the **repeated card**. A shell element that exists before the cards
  (`#ProductsClass`) returns in 0.2-2.4 s with `found: 0` on every page.
- A "no results" search never matches the card selector, so that row pays the
  full timeout either way.

<Warning>
  **Guest Chrome is a purpose tool, not a batch engine.** It exists for
  `webrain_serp` (`engine=google|brave`) and for solving an interactive
  CAPTCHA/Turnstile, and its profile (`serp/<profile>`, kept unless `--fresh`) is
  what carries the clearance to the next call. It refuses new targets
  (`PUT /json/new` → 500; `-32000 "Failed to open a new tab"`), so a batch there
  attaches the page it already has and runs **one serial tab** — measured 8 URLs
  in 5.65 s versus **1.46 s** on a real Chrome with `concurrency: 4`. Route bulk
  work to real Chrome, obscura or lightpanda.
</Warning>

## Crawl — whole sites

`webrain_crawl` (mode: `spider`) crawls from a seed URL with BFS (or DFS /
BestFirst):

```json
{
  "mode": "spider",
  "seed_url": "https://example.com",
  "max_depth": 3,
  "max_pages": 200,
  "allow": ["/product/"],
  "deny": ["/cart", "/login"],
  "autothrottle": true,
  "crawldir": "crawls/site-a"
}
```

Highlights:

- `allow` / `deny` URL-regex filters prune `/cart`, `/login`, images at crawl
  time
- `autothrottle` — adaptive per-domain delay: speeds up on fast servers,
  doubles on a blocked/error page, capped by `autothrottle_max_ms`
- `crawldir` — checkpoint/resume: persists `{queue, seen, results}` atomically
  every `checkpoint_every` pages; re-run with the same `crawldir` to continue
  (returns prior + new results, never re-fetches). Deleted on clean finish.
  `max_pages` counts the whole crawldir — raise it on resume to fetch more.
- `concurrency` — parallel tabs on real Chrome/obscura (default 4);
  single-target/lightpanda auto-serializes
- `crawl_timeout_secs` — hard wall-clock cap
- `respect_robots`, `keywords` (BestFirst scoring), `no_content` (link-only
  fast path)

## Sitemap — discover everything first

`webrain_crawl` (mode: `sitemap`) follows robots.txt `Sitemap:` →
sitemap_index → leaf sitemaps
→ every `<loc>`. Pure HTTP, no browser:

```text
webrain_crawl(mode="sitemap", url="https://example.com")
→ { urls: [...], count, sources }
```

Feed the URLs into `webrain_batch` for a full crawl.

## Validation & filtering

- `webrain_crawl` (mode: `validate`) — HEAD-then-GET check; filters 404s/5xx
  before a batch
- `webrain_extract` (mode: `bm25`) — keep only top-k relevant items after
  extraction
